# ASSETIQ
**AIoT Universal Asset Health & Predictive Maintenance Platform**
*"One Intelligence Layer. Multiple Assets. Predictive Maintenance."*

A React + Vite dashboard demonstrating a single AIoT intelligence layer that
monitors an Industrial Motor prototype today (ESP32 + temperature +
vibration + IR/Hall sensor) and is architected to support EV Motors, EV
Batteries, Pumps, Compressors and Generators through the same pipeline:

```
Sensor Data → Asset Baseline → Anomaly Detection → Asset Health Score → Explainable Warning → Maintenance Recommendation
```

## Run it

```bash
npm install
npm run dev
```

Then open the printed local URL (typically `http://localhost:5173`).

```bash
npm run build      # production build → dist/
npm run preview    # preview the production build
```

## What's simulated vs. real

Every value in this build is generated by `src/services/sensorService.js`
and `src/data/simulatedData.js`. Cards and pages that show simulated data
are labeled **DEMO DATA** in the UI. The **LIVE SENSOR DATA / DEMO DATA**
toggle in the top bar and in Settings is wired up and ready — it currently
falls back to simulated data either way, since no ESP32 is connected yet.

## Connecting the real ESP32 prototype

`src/services/sensorService.js` is the single seam between the UI and the
data source — no other file needs to change.

1. Have the ESP32 (with temperature, vibration/accelerometer, IR/Hall and
   optional current sensors) post readings over Wi-Fi to a small API you
   stand up, in this shape:

   ```json
   {
     "assetId": "AST-IND-001",
     "assetType": "industrial_motor",
     "temperature": 48.6,
     "vibration": 2.31,
     "cycles": 1842,
     "current": 4.2,
     "timestamp": "2026-09-24T10:42:18"
   }
   ```

2. Replace the body of `fetchLiveReading()` in `sensorService.js` with a
   `fetch()` call to that endpoint.
3. Leave `startReadingStream()`'s signature untouched — every page/component
   subscribes through it via `DataContext`, so no UI code needs to change.
4. If the live fetch fails, the stream automatically falls back to
   simulated data rather than breaking the dashboard mid-demo.

## Project structure

```
src/
  components/     Sidebar, Header, MetricCard, HealthScore, SensorChart,
                   SensorOverview, AnomalyPanel, AlertPanel, MaintenanceCard,
                   AssetSelector, AssetPassport, DemoMode, BatteryPanel
  pages/          Dashboard, Assets, Monitoring, Analytics, AnomalyDetection,
                   Maintenance, AssetPassportPage, Alerts, Settings
  data/           assetData.js (per-asset-type config), simulatedData.js
  utils/          healthScore.js, anomalyDetection.js
  services/       sensorService.js  ← ESP32 integration point
  context/        DataContext.jsx   (global state: selected asset, demo
                   mode, live reading, computed health/anomaly)
```

## Demo Mode

The Demo Mode panel (Dashboard and Maintenance pages) drives **every** panel
— sensor cards, charts, health score, anomaly score, alerts and maintenance
recommendation — from one of three simulated states: `NORMAL`, `WARNING`,
`CRITICAL`. Critical mode only ever changes on-screen numbers; it never
issues any command to real hardware.

## Language and scope

The Asset Health Score and anomaly detection in this build are heuristic,
explainable condition-monitoring tools, not a validated mechanical-failure
diagnosis. The UI intentionally avoids language like "bearing failed" in
favor of "abnormal vibration detected" / "inspection recommended". Remaining
Useful Life and failure prediction are shown as roadmap items that require
historical run-to-failure data ASSETIQ doesn't have yet.
